The problem

AI agents write fast. They also break things quietly.

The code compiles, the agent says "done" — and the damage surfaces three commits later. These are the four failures every AI-assisted developer has already met. Each one has a specific guard in the harness.

✕Edits the wrong file

You asked for a one-line fix in the login handler. The agent "cleaned up" the whole auth module while it was in there — and your custom session handling, the part that actually worked, was rewritten away.

# what you asked fix the redirect in login.php line 42 # what got committed auth.php · session.php · login.php 3 files rewritten — 412 lines changed

Guarded by safe-editing — surgical edits only: change what the task requires, never rewrite code that already works.

✕Invents APIs that don't exist

The code reads beautifully. It just calls a method that was never in the library — so it passes review, gets merged, and crashes the first time that path runs in production.

// agent's "fix", merged as-is const user = await db.findUserByEmailFast(email); // runtime, two days later TypeError: db.findUserByEmailFast is not a function

Guarded by no-hallucination — only packages, APIs and functions that exist in your project or its docs get used.

✕Ignores your conventions

Your codebase has a way of doing things — prepared statements, your naming, your folder layout. The agent never looked. Its code works, but it's written in a dialect nobody on the project speaks.

# your project, everywhere $stmt = $pdo->prepare("SELECT … WHERE id = ?"); # the agent's new file $r = mysqli_query($db, "SELECT … " . $_GET['id']);

Guarded by safe-editing + debug-first — Rule #4: read the surrounding code and match its discipline before writing a line.

✕Ships untested changes

"Done!" — except nothing was run. The renamed export is imported by six other files, the build is red, and you find out from CI, or worse, from a user.

> rename getUser() to fetchUser() ✓ Done! Renamed in userService.js. # 6 other files still import getUser() # no test run · no build run · no report

Guarded by debug-first + Rule #6 — validate every change, then report exactly what changed. "Done" has to be earned.

Under the hood

What sync actually puts in your project.

No magic, no daemon, nothing phoning home. reviewer-harness sync writes plain files into your project — each runtime's own native format — and you can open every one of them and read exactly what your agent will read.

your-project/ ├── harness.config.json ← the master config — the one file you edit ├── CLAUDE.md ← Claude Code ├── GEMINI.md ← Gemini CLI ├── .clinerules ← Cline ├── .opencode/ │ ├── instructions.md ← OpenCode │ └── commands/ ← every skill as a slash command ├── .qoder/skills/ ← Qoder skill bundles ├── .github/skills/ ← Copilot CLI skill bundles └── .agents/skills/ ← Freebuff · Antigravity # every file sync overwrites is backed up # first — same name, .bak extension

One source of truth

Your rules and skills live once, in harness.config.json. Sync renders them into each runtime's format — edit in one place, and all 8 runtimes agree.

Readable, not magic

Every generated file is plain Markdown you can open, diff and commit to git. If you stop using the harness, the files are just text — delete them and nothing breaks.

Secrets never sync

Before writing anything, sync scans your config for leaked keys and tokens — and blocks the sync if it finds one. Your credentials never land in an instruction file.

Install

Running in under a minute.

Three steps. The harness validates your config, scans it for leaked secrets, and writes each runtime's native instruction file — with a .bak backup before anything is overwritten.

1

Install the CLI

One global install. Zero dependencies — if you have Node.js 18+, you're ready.

$ npm install -g reviewer-harness
2

Go to your project

Every command works on the current directory — the harness lives inside your project, next to your code.

$ cd your-project
3

Init, then sync

init creates your master config. sync pushes the rules, skills and prompts into every runtime you enable.

$ reviewer-harness init && reviewer-harness sync
Set it up once

Run reviewer-harness global once and every skill becomes a slash command in every project you open — no per-project setup. Preview any sync first with reviewer-harness sync --dry-run — it writes nothing.

Zero-install: npx reviewer-harness skills add safe-editing macOS / Linux: curl -fsSL …/bin/install.sh | bash Windows: irm …/bin/install.ps1 | iex No Node? Run it via Docker

The rules

Six rules. Synced everywhere.

These ship in the master config and land in every runtime's instruction file — so every AI you code with plays by the same guardrails.

R—01

Edit surgically

Change only the code the task requires — never rewrite a whole file.

R—02

Never invent dependencies

Use only libraries already in the project. No made-up package names or APIs.

R—03

Test before “done”

After coding, run the tests or lint before saying the task is finished.

R—04

Read before you change

When unsure about existing code, read the surrounding files first.

R—05

Use the project memory

Read memory/INDEX.md before coding — decisions, gotchas, do-not-touch files — and write back what you learn.

R—06

Validate and report every change

After editing any code, run validation, then report every file changed with the actual output. A change is not done until it has been validated and reported — never finish silently.

FAQ

Straight answers.

No fine print — starting with the question everyone asks first.

Is it really free?+

Yes — completely. The install, all 34 skills, all 8 runtimes, sync, updates — everything is free. reviewer-harness is MIT licensed and published free on npm and GitHub. There is no paid tier, no trial, no Pro version, and nothing to buy. No account, no card, no catch.

Which agents does it work with?+

Eight runtimes: Claude Code, OpenCode, Gemini CLI, Cline, Freebuff, GitHub Copilot CLI, Antigravity, and Qoder. One harness.config.json syncs your rules, skills and prompts into each one's native instruction format — switch agents whenever you like and your setup comes with you.

What happens to my existing instructions when I sync?+

Sync writes the harness instruction files — CLAUDE.md, GEMINI.md, .clinerules and the rest — into your project, and every file it overwrites is backed up first with a .bak extension. If you already keep custom instructions in those files, back them up yourself before your first sync and merge what you want to keep into harness.config.json, so it survives every future sync.

Do the skills apply automatically?+

Yes. After sync, the rules and enabled skills live inside your agent's own instruction files, so they apply on every task, in every session — there is nothing to remember to turn on. When a task needs one specific discipline, every skill is also a slash command: type /audit-team, /system-design or /explain to focus that skill on demand.

Does it need an internet connection or an API key?+

No. reviewer-harness has zero dependencies and runs entirely on your machine — it only reads and writes files inside your project. No API key, no telemetry, no network calls. The only download is the one-time install from npm (or run it with npx).
